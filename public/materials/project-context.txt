# Adaptive Learning Analytics Platform — architecture project

English translation of the original project context. This historical source describes the initial blueprint; the website and docs/concept.md reflect the later seven-system architecture and learning journey simulator. The original Russian attachment is retained in the repository under docs/source-archive and is not published as website content.

The concept has been combined into a system project that can be implemented gradually without interrupting active educational programs.

Five principles form the foundation: a shared educational data model; separate versioning of learning materials and learning plans; automatic version pinning for students; traceable analytics from Moodle, GitLab and Sheets; and gradual modernization of the existing AsciiDoc plugin.

Two pilot courses validate the architecture: Foundations of AI, an individual online course with HTML versions and Moodle results; and Java Dual Training, a group program with different assignments, deadlines and GitLab Merge Requests.

The central decision is that the number of Moodle activities must not define completion percentage. Progress is calculated against obligations in the student's individual learning plan.

The architecture package also includes requirements for historical data, manual migrations between versions, MR matching quality and reproducible calculations.

## Suggested sequence in the original proposal

1. Visualize the architecture first. Create a GitHub repository, add the package and use its implementation brief. The initial result is an interactive site with diagrams, terminology, two learning models and examples of versioning and progress transfer.
2. Audit Moodle and GitLab. Determine how the plugin saves grades, what data is available, how HTML builds work and whether Java MRs can be linked to Moodle assignments.
3. Build the first working MVP. Connect the two pilot courses, form learning plans and calculate progress without changing existing courses.
4. Add versions and migrations. Pin releases for new students, detect outdated learning records, preview transfer rules, and enable changes only after verification.
5. Develop the content platform. Gradually extract HTML interactions into independently versioned components with a shared contract while retaining existing AsciiDoc builds.

## What needs verification before implementation

These documents describe a target architecture. They do not claim that existing Moodle plugins and GitLab repositories already support every mechanism. Points requiring verification against the actual infrastructure are identified separately.

Moodle External Services and Events APIs can support parts of the integration, but access to grades, attempts and custom events depends on the deployed Moodle version, settings and plugin. GitLab APIs and webhooks support MR ingestion; they cannot independently determine which learning assignment has been completed.

The original recommendation was to use the package as both a discussion document and an implementation brief. Begin with an interactive model using synthetic records to identify contradictions in versioning, assignment and progress logic before changing active courses.
